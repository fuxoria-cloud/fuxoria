## 插件来源

原包包含 13 个 addon、1 个 captcha、1 个 certification、3 个 gateway、2 个 mail、1 个 oss、8 个 reserver、3 个 server 和 1 个 sms 插件。完整目录名单在 `reference/inventory.json`。

支付目录实际只有 `ali_pay_dmf`、`wx_pay`、`user_custom`。微信原实现是独立 wx_pay 模块，支付宝是 ali_pay_dmf 模块。易支付和虎皮椒没有随这个仓库提供，应按其公开协议另行实现并单独联调，不能写成原插件已直接移植。未知的商业插件、商店授权和在线服务账号不属于仓库已包含的内容。

对 `app/**/*.php` 和 `public/plugins/**/*.php` 的编码器标记扫描没有发现 ionCube 编码文件候选。`app/admin/model/PluginModel.php` 与 `app/admin/controller/AppMarketController.php` 的安装流程会检查 ionCube Loader；这说明应用商店安装可能有运行时要求，不能据此断言仓库已有代码加密。静态扫描也不能排除其他形式的混淆。

## 迁移前的隔离检查

先从旧系统的只读备份恢复一份隔离数据库。关闭隔离环境的支付通知、短信、邮件和开通任务出口，防止演练触发真实扣款或重复开通。保留备份校验值、源码提交、数据库版本、时区、表前缀、启用插件版本和实际后台路径。

第一轮只生成导入预览：列出每张表的行数、空值、重复邮箱、孤立外键、金额范围、货币、时间字段，以及新旧字段映射。预览不写旧库，也不覆盖新库。无法识别的状态或插件配置应给出具体记录标识，留待人工处理。

旧 API 的路径和响应格式需要专门的兼容验收。新版 `/api/v1` 是新接口，不能凭字段相近就假定老客户端、上下游和旧模板可以直接调用。若需兼容，应为旧调用方提供明确的兼容入口，逐条对照旧接口样本。

## 账号和密钥

`app/common.php:609` 的普通 V10 密码算法是 `###` 加 `md5(md5(AUTHCODE + password))`，比较函数在同文件第 646 行。文件还包含 Zkeys 历史密码分支，不能把所有旧账号都当同一算法。

导入时记录原密码算法和原摘要，绝不尝试恢复明文。选择兼容登录时，原 `AUTHCODE` 只通过受控密钥配置提供；第一次通过旧算法验证后，立即生成新版密码摘要并清除该账号的旧验证材料。无法取得原验证材料的账号走已验证邮箱或手机的密码重置流程。管理员与用户账号分别核对，所有旧会话失效后重新登录。

支付私钥、云平台密码、API 密钥和对象存储凭据不能复制进源码或迁移报告。先建立旧凭据用途清单，再通过新系统的密钥配置重新录入或轮换。迁移测试只使用沙箱或隔离账号。

## 余额与账本

金额以十进制文本读取，按原货币小数位精确转换，禁止先转成 JavaScript 浮点数。原始金额、货币和对应记录 ID 要保留在迁移对账资料中。出现超出精度的金额时终止该批次并报告具体记录，不能静默舍入。

切换前冻结旧系统的充值、抵扣、提现、退款、人工调账与支付回调写入。等待进行中的支付查单和资金任务收敛，再取最终快照。为每个用户、每种货币核对旧余额、冻结额、未支付订单、在途退款和提现；不能只对比全站总额。

期初余额以独立的迁移分录写入新账本，并带上来源快照和旧用户 ID。历史交易按来源导入档案，避免把历史支付回调再次当作新收入。新旧期初对账通过之前，保持资金写入关闭。

## ID、状态与时间

建立 `(source, entity, legacy_id) → new_id` 的唯一映射，覆盖用户、订单、商品、服务、工单、交易和插件数据。再次导入同一来源记录应复用映射，不能产生第二笔交易或第二台实例。

先导入被引用的主体，再导入关联记录；结束后检查孤立关系和重复映射。服务除了业务 ID，还要保留云平台资源 ID、所属上游与机房，避免切换后重新开通已经存在的资源。每个原状态都要列出对应的新状态和允许动作，无法对应的状态不自动推进。

旧 Unix 时间戳按 UTC 瞬间解释，展示使用站点配置的时区；没有时区的文本日期先核实来源。续费周期按原订单约定迁移，不把“月”统一当固定 30 天。

## 演练、切换和回滚

1. 在空的新库执行演练，保存导入预览、映射结果、逐用户资金对账和服务资源核对报告。
2. 再执行一次同样的导入，验证幂等；随机抽查老账号登录、订单、账单、工单和服务生命周期。
3. 用沙箱支付验证重复、乱序、延迟、错误金额、错误货币和错误商户回调。验证任务中断重试不会重复开通或重复记账。
4. 切换时开启维护窗口，冻结旧库写入和外部任务，完成最终快照及差量导入，再对账。先开放只读查询，检查通过后逐项放开新系统写入。
5. 保留旧库与备份，禁止新旧开通守护进程同时消费同一业务。DNS/CDN 切换同时清理受影响的公共缓存，私有页面禁止共享缓存。

新系统还没有接受资金和资源写入时，可以停止新服务、恢复旧系统入口并解除旧库冻结。新系统已经接受写入后，直接恢复旧快照会丢失这些交易；应先冻结新写入、导出切换后的增量，对每笔资金和资源操作核对并完成受控回迁，再恢复旧系统。回滚是否成功，以逐笔对账和外部资源核对为准。

## 验收证据

`reference/inventory.json` 里的每个条目初始状态都是 `pending`。更新某条状态时，应同时填写新实现位置、实际验收入口和结果记录。一次通过的功能验收要能在隔离环境重跑，不能只附界面截图。

核心判据包括：原功能的成功与失败行为可解释；越权访问被拒绝；订单和资金的重复请求不产生额外副作用；插件增删不用修改中央登记；手机主要操作有足够点击区域；公共缓存不会包含客户数据；修改公共内容时只刷新受影响的产物。性能指标必须附带环境、负载和实测结果，不能以“高性能”字样代替测量。

## 空库导入与初始化配置

`scripts/import.ts` 只向独立空业务库导入，允许保留一个未导入的bootstrap管理员。完整迁移自动创建的一条原始联盟设置和一条CNY币种锚种子可保留：工具逐字段比对规则、金额、等待期、启用状态及币种名称、币符、精度、汇率与默认状态。配置改动或额外币种仍视为已有业务；账本、客户、订单、资源、审计等表继续要求为空。

CNY月付服务在导入计划中明确保存合同币种、月数、固定秒数与原续费价。原流水和期初负债使用各自真实来源，任何晚期外键或会计检查失败都会回滚整轮。操作步骤与8项隔离回归见 [原系统数据导入](data-import.md)。
