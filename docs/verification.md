## 运行

```bash
npm run test:integration
```

先安装项目依赖，并在受控环境或根 `.env` 中提供可连接的 `DATABASE_URL` 与 `REDIS_URL`。数据库账号需有创建和删除专用测试库的权限，Redis 需支持逻辑库 14。测试每次都会构建最新支付包和 API，按文件名执行全部 `database/migrations/*.sql`，不会拿旧 `dist` 代替当前源码。

测试固定使用 `yunzou_integration_test`、API 端口 `3303` 和 Redis DB14。开始时通过数据库互斥锁防止两套同名测试同时运行，清理专用测试库的上次残留，再建新库。上述数据库名属于测试预留范围，不应存放业务数据。

测试进程的站点来源为 `https://yunzou.test`，易支付网关为 `https://pay.example.invalid/submit.php`。审计密钥、测试密码和易支付密钥每轮随机生成，只注入临时进程；根 `.env` 和 dev 服务配置不会改写。支付测试生成协议 URL 和真实 MD5 签名回调，不连接该无效域名，不使用真实商户，也不在 dev 环境开放模拟付款接口。

结束时停止 API 和 Go 进程，关闭连接，删除专用测试库与临时二进制。Redis 仅删除本轮明确记录的会话、邮箱限流键以及专用 DB14 的本机限流键，不执行 `FLUSHDB`，不访问 dev 的逻辑库。断言失败也会走同样的清理流程。

## 审计验链

```bash
npm exec tsx scripts/verify-audit.ts
```

脚本使用 `DATABASE_URL` 与 `AUDIT_KEY`，开启只读可重复读事务，按数值 ID 分页检查：

- 每条 `previous_hash` 是否接上前一条签名。
- 保存的 `canonical_body` 是否能通过 HMAC-SHA256。
- 原文中的操作者、动作、对象、详情和前一锚点是否与数据库可查询字段一致。

输出只包含已验证数量、历史格式数量、最后 ID 与链尾锚点。密钥必须与数据库分开保管。若对固定快照另有独立保管的期望链尾，可通过 `AUDIT_EXPECTED_HEAD` 比较；只有库内链而没有外部锚点时，无法仅靠数据库发现整个尾部被删除。

`003_audit_payload.sql` 之前的记录可能没有 `canonical_body`。脚本会按原五字段的 `JSON.stringify` 格式尝试恢复；能够通过 HMAC 的旧节点会计入 `historicalCount`。旧 `details` 已进入 JSONB 后，属性顺序可能与最初签名的 JSON 不同，原始字节不一定可恢复。此时脚本明确失败并要求原始签名文本或旧导出，不把该记录报告为已验证，也不擅自重签历史。

集成测试同时覆盖可恢复的空详情旧记录，以及确实因 JSONB 重排键而无法复原的样本。后者是专用库内故意建立的边界夹具，预期结果就是验链拒绝。

## 本轮修复与检查
